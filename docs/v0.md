# v0 — Implementation Spec

> **Status: shipped.** v0 acceptance is met. This document is retained as the historical contract for the bootstrap slice; it describes the substrate as it was first built. Current development tracks the v1 substrate list in `docs/spec.md`.

This document is the implementation contract for the slice that closes the **v0 Acceptance** criteria in `docs/spec.md`. The system spec stays the source of truth; where the two disagree, this one is wrong.

This spec is written under the principle ordering in `AGENTS.md`: convergence is the model, the event log is the system, bounded patience is the convergence invariant, idempotency is a load-bearing technique. Code that conflicts with that ordering is a bug regardless of what this document says.

## Goal

When the slice is done, the bootstrap thesis is live:

1. Owner dictates an instruction from the iPhone Shortcut → a `work_item` exists in the system within 15 s, attributed to the iPhone token.
2. A Cursor agent, over MCP, lists open items, picks one, appends progress events, spawns children, and marks items `done`. Every event attributed to the Cursor token.
3. The same instruction sent twice produces one `work_item`, not two.
4. All state survives a process restart.
5. Each "v1 Substrate" item in `docs/spec.md` exists as a `work_item` in the running v0 system before v1 work begins.

## In Scope

- Bearer-token auth with one root token + minted client tokens.
- `meristem tokens` CLI (`create`, `revoke`, `list`).
- Idempotency middleware on every POST.
- The six v0 REST endpoints from `docs/spec.md`.
- An events writer with deterministic ids and full attribution.
- A synchronous projection layer that derives non-`events` rows in the same transaction as the event append.
- An MCP server (stdio) with one tool per REST op; current v1-directed work
  also mounts a read-only Streamable HTTP MCP endpoint at `/mcp` on
  `meristem api`.
- The iPhone Shortcut contract.
- A `meristem seed v1` step that loads the v1 backlog into the running system.

## Out of Scope (deferred to work_items inside the running v0)

Per `docs/spec.md` "What v0 Deliberately Does Not Have": approvals, connectors, **the convergence loop itself**, multi-modal messages, token scopes, web UI, webhooks, rate limits, artifacts, intent classification.

> ### Note on bounded patience
>
> The convergence-loop / reconciler is deferred. v0 work_items can therefore sit in non-terminal states (e.g. `captured`) indefinitely until the owner or an agent transitions them. **This deliberately violates the bounded-patience principle** and is the single most important thing v1 fixes. The schema, event taxonomy, and projection layer in this spec are all designed so a convergence loop can be added in v1 without restructuring anything.

## Architecture

The data model is event-sourced:

- **`events`** is truth. Append-only, deterministic ids, no `UPDATE`/`DELETE`/`TRUNCATE`.
- **All other tables are projections.** `messages`, `message_parts`, `work_items`, `work_item_relations`, `tokens`, `idempotency_keys` are derived rows. Dropping any of them and folding the event log through the projection writers reproduces them byte-for-byte (modulo timestamps).
- **Handlers append events.** They do not `INSERT` into projection tables. Within the same transaction, registered projection writers fire and produce the derived rows. After commit, the handler reads back from the projection to build the response.

This is "strong" event sourcing: events are the only writable substrate; projections are pure functions of the log. The cost is a small synchronous projector layer; the payoff is that the principle in `AGENTS.md` is *enforced*, not aspired-to, and projection migrations become "drop and rebuild" rather than ad-hoc data fixes.

`tokens` and `idempotency_keys` are projections too. The events `token.created` and `token.revoked` drive `tokens` rows; idempotency entries are written by the middleware via `idempotency.recorded` events. This means token rotation, replay, and audit recovery all use the same code path as everything else.

## Package Layout

Adds to the existing tree without restructuring it:

```
internal/
  auth/         token store + bearer middleware
  domain/       pure types: Token, Message, WorkItem, Event
  events/       append-only writer; deterministic ids
  projections/  registered writers (events → derived rows), all in same tx
  idempotency/  middleware + projection writer
  inbox/        message capture handler + supporting domain logic
  workitems/    lifecycle, transitions, relations
  feed/         chronological projection
  api/          (existing) wires routes, adds handlers
  mcp/          MCP tool definitions + stdio and HTTP dispatch
cmd/meristem/
  tokens.go     'meristem tokens'
  mcp.go        'meristem mcp'
  seed.go       'meristem seed v1'
```

`internal/domain` does not import any transport or projection package. Both transports import `internal/domain` and call domain functions. Projection writers import `internal/domain` and `internal/storage` only.

## Auth

- A single **root token** mints every other token; the root's secret is shown once on creation and never persisted in plaintext.
- Each client (iPhone, Cursor instance, web session, CLI) holds its own token row. Names are operator-chosen.
- Tokens are 32 bytes from `crypto/rand`, base64url, prefixed `mrs_` for grep-ability.
- Storage hash is **SHA-256**, constant-time compare on lookup. Tokens are random, not passwords.
- Each token has a `source` classification: `human`, `agent`, or `system`. Request bodies may describe upstream provenance, but event authority comes from the authenticated token row.
- Wire: `Authorization: Bearer mrs_…`. Middleware attaches a `*Token` to the request context; handlers never touch the raw bearer.
- Token rows are projections of `token.created` and `token.revoked` events. The `meristem tokens create` CLI subcommand appends the event; the projector writes the row.
- Bootstrap: `meristem tokens create --root` is the only way to mint root, and it errors if a root already exists. Rotation: `--replace`. Client tokens use `--source human|agent|system` so attribution is explicit at creation time.

## Idempotency Middleware

- Applies to every POST. Missing `Idempotency-Key` → 400 `idempotency_key_required`. v0 enforces this universally; loosening per route is its own future work_item.
- Lookup key: `(token_id, METHOD + PATH, key)` — the schema's `scope` column.
- `request_hash` = SHA-256 of canonical JSON body. Same key + same hash → return stored `(status, body)`. Same key + different hash → 422 `idempotency_key_conflict`. Miss → handler runs, response captured, then returned.
- The middleware emits an `idempotency.recorded` event with the captured response; the projector writes the `idempotency_keys` row. This means idempotency state is rebuildable from the log like everything else.
- While a miss is executing, the middleware also places the canonical idempotency identity into request context. Write services derive any newly-created subject ids from that identity, so a retry that reaches the handler before the response cache exists still converges on the same `message` or `work_item` event subjects.
- TTL 24 h. Cleanup is a periodic worker — a v1 work_item.

## Events

- Every state-changing operation appends exactly one `events` row.
- `events.id = uuid(sha256(subject_kind || ':' || subject_id || ':' || kind || ':' || canonical(payload))[:16])`. Replays of the same logical event are no-ops; PK conflict is treated as success.
- `actor_token_id` and `source` come from the request context. The seed command uses a dedicated `system` token, not root.
- Canonical event kinds for this slice:
  - `token.created`, `token.revoked`
  - `idempotency.recorded`
  - `message.captured`
  - `work_item.created`, `work_item.transitioned`, `work_item.event_appended`, `work_item.relation_added`

Adding a new kind is a deliberate change: extend the constant, register a projector, document it here.

## REST Contracts

JSON in, JSON out. Error shape: `{ "error": { "code": "...", "message": "..." } }`.

### `POST /v1/inbox/messages`

```json
{ "source": "human", "text": "Build the approval system in meristem" }
```

`source` defaults to `"human"`; v0 only accepts `"human"` here, and the bearer token must also be classified as `human`. `text` required, non-empty.

201:

```json
{ "message_id": "uuid", "work_item_id": "uuid", "captured_at": "rfc3339" }
```

v0 has no intent classifier, so the rule is hardcoded: **every captured human message also creates a `work_item`** with `title = first 80 chars of text`, `body = text`, state `captured`. The handler appends two events, `message.captured` and `work_item.created`, in one transaction. The projectors write `messages`, `message_parts`, and `work_items` rows from those events.

### `GET /v1/feed`

Two modes:

- **Snapshot (back-compat)** — no `cursor`, no `wait`:
  `?limit=50`. Returns the latest feed-visible events newest-first under
  `{ "items": [...] }`. Default 50, max 200.
- **Watcher / resumable** — `?cursor=<opaque>&wait=<duration>&limit=<n>`:
  returns feed-visible events strictly after the opaque cursor in
  oldest-first order under
  `{ "items": [...], "next_cursor": "opaque", "has_more": true|false }`.
  The consumer persists and round-trips `next_cursor` verbatim; it does
  not parse it. Delivery is at-least-once, so consumers dedupe by
  `event_id`. `wait` is bounded long-poll (server-capped) and returns as
  soon as matching events arrive or the timeout expires. Unknown or
  malformed cursors return `400 invalid_cursor`.

Feed is still a chronological projection over `events`, filtered to
user-meaningful kinds (`message.captured`, `work_item.transitioned`,
`work_item.created`, and later feed-visible additions).

### `GET /v1/feed/stream`

Server-Sent Events push channel for the same feed-visible events
`/v1/feed` serves. Long-lived HTTP connection; the server emits one
SSE frame per event as it lands:

```
id: <opaque cursor>
event: feed
data: <one-line JSON envelope, identical to a /v1/feed item>
```

Heartbeat comments (`: keepalive`) are sent on idle to keep middleboxes
from closing the connection. Resume after disconnect by sending the
last cursor as the SSE-standard `Last-Event-ID` header (or `?cursor=`
query param for callers that can't easily set headers); the server
replays events strictly after that cursor before resuming live push.
Fabricated or unknown cursors return `400 invalid_cursor` and the
client should reconnect without `Last-Event-ID` to restart "from now".

`/v1/feed?cursor=` remains the explicit snapshot/replay path; the
stream is for live tailing.

### `GET /v1/work-items` and `GET /v1/work-items/{id}`

List supports `?state=&limit=&cursor=`. Detail returns the projection row + parent/child ids + last 50 events on it + the latest message.

### `POST /v1/work-items` and `POST /v1/work-items/{id}/children`

`{ "title": "...", "body": "...", "suggested_convergence_checks": ["..."], "human_review_status": "waved_through" }` → 201 `{ "work_item_id": "uuid" }`. `suggested_convergence_checks` is optional and defaults to `[]`; `human_review_status` is optional and defaults to `waved_through` (`blocked | waved_through | approved`). Appends `work_item.created`; children also append `work_item.relation_added`. Projectors write the rows.

### `POST /v1/work-items/{id}/events`

`{ "kind": "string", "payload": { ... } }`. Free-form; `kind` is operator-chosen but conventionally namespaced (`agent.tool_used`, `cursor.commit_made`). Stored as a `work_item.event_appended` envelope; the inner kind and payload are visible in `payload.inner_kind` and `payload.inner`. Projector updates `work_items.updated_at`.

### `POST /v1/work-items/{id}/metadata`

`{ "suggested_convergence_checks": ["..."], "human_review_status": "waved_through" }`. Sets the complete metadata declaration for the work item. Appends `work_item.metadata_updated`; projector updates `work_items.suggested_convergence_checks`, `work_items.human_review_status`, and `updated_at`.

### `POST /v1/work-items/{id}/transition`

`{ "to": "running", "reason": "string?" }`. Server validates against the lifecycle in `docs/spec.md`. Illegal → 409 `invalid_transition`. Appends `work_item.transitioned`; projector updates `work_items.state` and `state_reason`.

## MCP Tool Surface

One tool per REST op, dot-namespaced:

`inbox.capture`, `feed.read`, `deterministic_errors.list`, `deterministic_errors.get`, `work_items.list`, `work_items.get`, `work_items.create`, `work_items.spawn_child`, `work_items.append_event`, `work_items.update_metadata`, `work_items.transition`.

Cursor currently filters MCP tools whose names contain `.`. The canonical
surface remains dot-namespaced, but launching `meristem mcp` with
`MERISTEM_MCP_TOOL_NAMES=cursor` advertises underscore aliases
(`feed_read`, `work_items_list`, etc.) while dispatch still accepts both
the canonical names and aliases.

`feed.read` mirrors `GET /v1/feed`: omit `cursor` and `wait` for the newest-first snapshot (`{ "items": [...] }`); set either for watcher mode (`{ "items", "next_cursor", "has_more" }`) with `wait` as a Go duration string (e.g. `30s`), capped like the HTTP route.

### `meristem mcp` stdio

Auth: server reads `MERISTEM_TOKEN` from its environment on launch. Each Cursor
instance has its own token row; that row is the actor on every event it causes.
Stdio remains the compatibility/sandbox transport and exposes the full MCP tool
surface above, subject to token scopes.

The stdio reader accepts complete JSON-RPC objects from a stream, including
pretty-printed multi-line JSON, and writes compact one-line JSON responses.

Mutation tools require an explicit `idempotency_key` argument:

- `inbox.capture`
- `work_items.create`
- `work_items.spawn_child`
- `work_items.append_event`
- `work_items.update_metadata`
- `work_items.transition`

The MCP adapter removes `idempotency_key` before calling the underlying service
and runs the call through the same durable idempotency store as HTTP POSTs:
`token_id`, scope `MCP:<tool_name>`, caller-provided key, and a SHA-256 hash of
the canonical tool name plus arguments with the key removed. For the same
token, tool, key, and arguments, the recorded MCP tool result is replayed. For
the same token, tool, and key with different arguments, the adapter returns an
idempotency conflict before the tool mutates state. While a fresh call runs,
the adapter injects the idempotency identity into context so write services
derive stable subject ids.

### `meristem api` Streamable HTTP MCP

`meristem api` mounts `GET /mcp` and `POST /mcp` as the shared-process MCP
endpoint. `POST /mcp` accepts one JSON-RPC message per request body and requires
the Streamable HTTP `Accept` shape: both `application/json` and
`text/event-stream`. Responses for JSON-RPC requests are returned as
`application/json`; JSON-RPC notifications and responses are accepted with HTTP
`202`. `GET /mcp` currently returns HTTP `405` because server-initiated MCP SSE
is not implemented.

HTTP MCP uses the same bearer middleware as REST, resolving the actor from
`Authorization: Bearer ...` per HTTP request. It dispatches directly through
`internal/mcp`; it does not proxy to `/v1/...`.

The HTTP MCP route currently advertises and permits only read tools:

`feed.read`, `deterministic_errors.list`, `deterministic_errors.get`, `work_items.list`, `work_items.get`.

HTTP MCP write tools stay disabled until the HTTP transport adds durable
mutation replay behavior equivalent to REST POST idempotency. When that route
is opened, it must use the same MCP argument-level `idempotency_key` contract
and `MCP:<tool_name>` scope as stdio; ambient HTTP `Idempotency-Key` headers are
not the canonical identity for JSON-RPC tool calls.

## iPhone Shortcut Contract

1. Capture spoken or typed text.
2. Generate a UUID for `Idempotency-Key`.
3. POST to `https://<host>/v1/inbox/messages` with bearer = the iPhone-specific token from iCloud Keychain.
4. Surface the returned `work_item_id` as a banner.

## Seed: v1 Backlog Into v0

After the slice ships, `meristem seed v1` idempotently appends one `work_item.created` event per item under "v1 Substrate" in `docs/spec.md`, each `captured`, attributed to the `system` token. Determinism comes from the event-id formula (subject_id is itself derived from the slug of the title), so reruns are no-ops. From that moment on, v1 is being built *inside* meristem.

The `system` token is created by the same `meristem tokens create --source system` flow, distinct from root.

## Sequencing (suggested PR order)

1. **auth + projections plumbing** — `internal/auth`, `internal/projections` skeleton, `tokens` CLI, middleware. The token-row projector is the first projector; it sets the pattern for everything below.
2. **events writer** — `internal/events`, deterministic ids, integration tests against Postgres.
3. **idempotency** — middleware + `idempotency.recorded` projector, exhaustive tests.
4. **inbox** — `POST /v1/inbox/messages`, message + message_parts + work_items projectors, integration tests covering the "two events, three projection rows" path.
5. **work_items writes** — create, spawn_child, transition, append_event, plus their projectors.
6. **work_items reads** — list, get.
7. **feed** — chronological projection.
8. **mcp** — eight tools, stdio server, `meristem mcp`.
9. **seed** — `meristem seed v1`, then run it.

Steps 1–3 establish the event-sourcing pattern. 4–7 are the REST surface built on it. 8–9 close the bootstrap.

## Acceptance Tests

Shell-runnable against a local stack:

1. **iPhone → work_item in 15 s.** `curl POST /v1/inbox/messages` with a fresh `Idempotency-Key`. Within 15 s, `GET /v1/feed` shows the message and the auto-created work_item.
2. **Cursor agent loop.** Drive an MCP client with a Cursor token through `list → append_event → spawn_child → transition done`. Verify each step's row in `events` carries the Cursor token id.
3. **Idempotency.** Same POST twice → one work_item, identical response, one `message.captured` event, one `work_item.created` event.
4. **Restart survives.** Run 1–3, restart, confirm everything visible via the API.
5. **Attribution.** For every event from 1–3, `actor_token_id` matches the issuing token.
6. **Projection rebuild.** `TRUNCATE` every projection table (not `events`) and run a rebuild script that folds `events` through the projectors. Diff the resulting rows against a snapshot taken before the truncate. They must match modulo timestamps that come from clocks rather than `events.occurred_at`.
7. **Bootstrap closed.** `meristem seed v1` produces one `work_item` per v1 substrate item, all `captured`, attributed to the `system` token.

Test 6 is what makes the event-sourcing principle real instead of decorative.

## Estimated Cost

5–7 focused days, matching `docs/spec.md`'s estimate. The strong-event-sourcing structure adds ~half a day of plumbing in step 1 and pays back through step 6 by eliminating most of the migration anxiety usually attached to a v0 schema.
